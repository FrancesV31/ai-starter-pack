# PRD — from brief to requirements document

Turn the idea or brief the user gives into a clear PRD. If the user didn't say what it's about, ask them first. If they point to a file (for example a brief made with the `shape` skill), read it first.

Use this structure:
1. **Summary:** one paragraph a busy executive can grasp in 20 seconds.
2. **Problem & context:** who, what pain, what evidence.
3. **Goals & non-goals:** explicit scope boundaries (non-goals matter most).
4. **Target users / personas.**
5. **User stories:** "As a ___ I want ___ so that ___", each tagged P0 / P1 / P2.
6. **Requirements:** functional, each with acceptance criteria.
7. **Success metrics:** one leading and one lagging indicator.
8. **Risks & open questions.**
9. **Rough phasing / milestones.**

Be concrete. Where information is missing, make a clearly labelled assumption instead of stalling, and list all assumptions at the end so the user can correct them.
